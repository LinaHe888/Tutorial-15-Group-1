# Task 4 — Short Report Paragraph + Video Script

## Report Paragraph

A realistic attacker for this app is a local reverse engineer or analyst who can inspect the APK and understand how authentication state is created. The decompiled code shows that the app stores an authenticated value named `sessionToken` in `SharedPreferences` after successful login, and that this value is generated by `generateSessionToken()` using `java.util.Random`. Because session tokens are security-sensitive values that should be unpredictable, this design weakens session integrity and reduces trust in the authenticated state. The threat is reinforced by the app's broader local security design, including plaintext credential storage in `credentials.txt` and fully local session handling.

## Video Script (Task 4 — ~45 seconds)

**[0-12s] Attacker Model**
"Our attacker is a local reverse engineer. They can install the app, decompile it with JADX, and inspect how authentication works. They do not need to be on the same network as the victim — all they need is the APK and a copy of their own session token."

**[12-25s] What the Attacker Learns**
"From the decompiled code, the attacker identifies three key facts. First, the app stores a value called `sessionToken` in `SharedPreferences` after login. Second, this token is generated by `generateSessionToken()`, which uses `java.util.Random`. Third, the app checks the token locally to determine if the user is authenticated — no server verification involved."

**[25-38s] Attack Path**
"The attack path is straightforward. Step one: decompile the APK. Step two: read one token from `SharedPreferences`. Step three: with the token and knowledge of the `java.util.Random` algorithm, recover the 48-bit seed in seconds. Step four: compute all future tokens offline. Step five: write the predicted token to `SharedPreferences` and open the app as the victim."

**[38-45s] Impact and Risk**
"The impact is session hijacking without any credentials. The attacker bypasses the entire login just by predicting the token. Even though this is a demo app, the same vulnerability pattern appears in real applications — session tokens must be unpredictable, and `java.util.Random` does not satisfy that requirement."
